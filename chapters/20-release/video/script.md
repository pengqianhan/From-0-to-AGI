### S05 标准格式

- 屏幕文字：架构名 Qwen3ForCausalLM → 三个框架直接能用
- 旁白：发布的第一件事是标准格式。一个 Hugging Face 目录：配置、权重、分词器，还有对话模板。权重用 safetensors，它只是一个头加上原始字节，不像 pickle 那样能藏代码。我们的架构和千问三的稠密模型逐层对应，导出时就写成它的名字，transformers、vLLM、llama.cpp 都不用改代码。对话模板必须和训练时逐字一致，冒烟测试里用 transformers 加载，logits 误差是零，模板也逐字相同。

### S06 内存 = 参数 × bit
- 画面：公式出现；三根横条：bf16 1.28 GiB、Q8_0 0.68 GiB、Q4_K_M 0.40 GiB；再加一根虚线条：32K 上下文的 KV cache 3.50 GiB。
- 屏幕文字：主线模型 689.5M 参数（暂定形状）
- 旁白：为什么要量化？因为内存约等于参数量乘以每个参数的位数。主线模型六亿九千万参数，用 {bf16|B F 十六} 要一点二八 {GiB|G}；八 bit 的 {Q8_0|Q 八零} 是零点六八；四 bit 的 {{Q4_K|Q 四 K}_M|Q 四 K M} 只要零点四。还有一个容易忽略的：三万两千长度的上下文，KV cache 要三点五 {GiB|G}，比四 bit 的权重大得多。在 CPU 上生成时，每一步都要把权重读一遍，权重小一半，速度就快不少。

### S07 分块：每 32 个数一个 scale
- 画面：一行 32 个小方格（真实权重，颜色深浅表示大小），上方一个橙色 scale 方块；公式 scale = max|w| / qmax、q = round(w / scale)、ŵ = scale · q；下方展示前 8 个数的 INT8 与 INT4 整数。
- 屏幕文字：INT8：qmax = 127　INT4：qmax = 7
- 旁白：量化的想法很简单。把一行权重每三十二个数分成一块，每块找一个缩放系数：块里绝对值最大的数，除以最大的整数格子。每个权重除以它、四舍五入成整数存下来，用的时候再乘回去。八 bit 有两百多个格子，数值几乎不变；四 bit 只有十五个格子，像零点零零二五这样的小数，直接被压成了零。

### S08 为什么要分块
- 画面：同一张带离群值的矩阵，三种 scale 范围：整张一个、每行一个、每块一个；右侧柱状图显示 INT4 误差 93%、36%、11.3%、8.3%（两级 scale）。
- 屏幕文字：一个离群值会撑大整组的 scale
- 旁白：为什么要分块？权重里总有少数特别大的离群值。如果整张矩阵共用一个缩放系数，一个离群值就把它撑大，其他几百万个数全被挤成零，四 bit 的误差高达百分之九十三。每行一个，降到百分之三十六。每三十二个数一块，降到百分之十一，代价只是每个数多存零点五 bit。再加上两级缩放，可以降到百分之八。

### S09 GGUF 的块长什么样
- 画面：两个字节条：Q8_0（2 字节 fp16 scale + 32 字节 int8 = 34 字节 / 32 个数 = 8.5 bit）；Q4_K（256 个数：2+2 字节超级块系数、12 字节 6 bit 子块 scale 和 min、128 字节 4 bit 整数 = 144 字节 = 4.5 bit）；下方 Q4_K_M：输出层与部分层 Q6_K。
- 屏幕文字：Q8_0 = 8.5 bit　Q4_K = 4.5 bit　Q4_K_M ≈ 混合
- 旁白：llama.cpp 用的 GGUF 格式，就是这个思路的工程版。{Q8_0|Q 八零} 每三十二个数一块，三十四个字节，正好是我们手写的八 bit 分块。{Q4_K|Q 四 K} 用两百五十六个数的超级块，里面八个子块各有一个六 bit 的缩放和最小值，超级块再存两个半精度系数，一共一百四十四字节，四点五 bit。最常用的 {{Q4_K|Q 四 K}_M|Q 四 K M} 还会给输出层和一部分注意力、前馈层多留 bit。我们的计算器照这个规则算，和 llama.cpp 实际量化出来的文件逐字节一致。

### S10 质量换大小
- 画面：左侧表格（第 10 章的小模型，0.86M 参数）：各方案的大小、Δloss、top-1 一致率；右侧 loss 随 bit 数变化的点线：8 bit 平、4 bit 小升、3 bit、2 bit 陡升（悬崖）。下方小字：Llama 3 8B：f16 6.233，Q8_0 6.234，Q4_K_M 6.407。
- 屏幕文字：8 bit ≈ 无损　4 bit 有代价　更低是悬崖
- 旁白：误差百分之十一听起来吓人，但模型关心的是预测变没变。把量化套在第十章的小模型上：八 bit 的 loss 变化在第四位小数，生成的文字一字不差。四 bit 分块，loss 升零点零零五，大约每十七个位置有一个最可能的字变了。三 bit 的代价是它的八倍，两 bit 的模型基本废了。llama.cpp 在八十亿参数的模型上测到的是同样的规律。量化的效果取决于具体的权重，所以发布前，一定要在自己的模型上量。

### S11 对拍：导出的还是同一个模型吗
- 画面：三列 token 序列对齐：zero（fp32）、GGUF f16、GGUF Q8_0，24 个 token 全部绿色对勾；第四列 Q4_K_M（tiny 回退成 Q5_0 + Q8_0）在第 10 个 token 变红分叉。上方：llama-tokenize 20 个 id 全部相同。
- 屏幕文字：同一提示词，贪心 24 个 token
- 旁白：导出之后，还是同一个模型吗？要对拍。写这一章时，我们用冒烟测试导出的 GGUF 文件和 llama.cpp 重新核对了一遍。同一句提示词，llama.cpp 分出来的二十个 token 编号和我们的分词器完全相同。贪心生成二十四个 token，zero 本身、{f16|F 十六} 和 {Q8_0|Q 八零} 的输出逐字相同。换成更低位的量化，第十个 token 就分叉了。这个小模型输出的其实是乱码，但对拍只关心一件事：两边算的是不是同一个东西。

### S12 本地运行与 demo
- 画面：左边笔记本图标：llama.cpp、Ollama（GGUF）；右边服务器图标：vLLM（safetensors，hermes 工具解析器）。下方终端窗口（极小配置演示）：`你：3 * (4 + 5) 等于多少？` `助手：`（空），旁边标注"调用 → 执行 → 喂回 的链路已通；模型太小，还不会用"。
- 屏幕文字：笔记本：llama.cpp / Ollama　服务器：vLLM
- 旁白：部署分两种。笔记本上用 llama.cpp 或者 Ollama，吃的是 GGUF 文件；服务器上用 vLLM，吃的是 safetensors 目录，打开 hermes 工具解析器，就能直接返回结构化的工具调用。本地 demo 是一个命令行助手：模型想调用计算器、日期或文件搜索，就在本地执行，再把结果喂回去。文件搜索只能在指定目录里找，工具的边界比模型的聪明更重要。冒烟测试里，这个一百三十万参数的模型回了一个空答案。链路是通的，模型还不会用，我们如实写下来。

### S13 模型卡与许可证
- 画面：一张模型卡从上到下展开：YAML 元数据、概要、数据与许可证、配方与花费、预注册、全部评测（含落后）、去污染、局限；占位格标"待训练"。右侧许可证选项：Apache-2.0（Qwen3、OLMo 2、SmolLM3）、MIT、社区许可证（Llama、Gemma）；数据：ODC-By、CC-BY 要求署名。
- 屏幕文字：只填有来源的数，没有的写"待训练"
- 旁白：最后是模型卡。它就是模型仓库首页的说明书：数据和许可证、每个阶段的配方和花费、预注册、全部评测结果，包括输的项、去污染检查和已知局限。我们的生成脚本只填有来源的数，没有的一律写待训练。权重用什么许可证，由作者决定：像千问三、OLMo 那样用 Apache 二点零，或者 MIT，或者自定义的社区许可证。但数据的署名义务不管怎么选都要履行，FineWeb-Edu 这类 ODC-By 数据要求署名。中间 checkpoint 也一起发布，让没有算力的读者能直接从我们的底座开始做实验。
