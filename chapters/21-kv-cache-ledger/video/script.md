## 二、分镜与旁白

### S01 片头
- 画面：章节标题卡淡入："第 21 章 / KV cache 的账本"，副标题"长上下文贵在哪，每个 token 该存多少"。
- 屏幕文字：第 21 章 · KV cache 的账本
- 旁白：第五部分开始了。这一部分讲过去两年开源模型的架构往哪里演进，答案几乎都指向同一件事：为了更长的上下文，要更小的 KV cache。这一章，我们先把这笔账算清楚。

### S02 回顾公式
- 画面：公式出现；代入主线模型的数字；下方两根横条：32K 对话的 KV cache（紫）与模型权重（橙）。
- 屏幕文字：2 × 层数 × KV 头数 × head_dim × 序列长 × 字节数
- 旁白：第十章我们算过：每一层、每个位置都要存一份 K 和一份 V。所以 KV cache 等于二乘层数、乘 KV 头数、乘 head_dim、乘序列长、再乘每个数的字节数。主线模型每个 token 要存 112 KiB，一条三万两千 token 的对话就是 3.5 GiB，比模型权重的 1.28 GiB 还大。长上下文到底贵在哪里？要分两个阶段看。

### S03 prefill：注意力随 T² 增长
- 画面：四根堆叠柱，分别是提示词 1K、4K、32K、128K；下段橙色是矩阵乘，上段紫色是注意力，标出注意力占比。
- 屏幕文字：注意力占比 7.8% → 25.4% → 73.2% → 91.6%
- 旁白：第一个阶段是 prefill，把整段提示词一次喂进去。运算量有两部分：矩阵乘法随长度线性增长；注意力要让每两个位置都算一次，随长度的平方增长。提示词一千个 token 时，注意力只占百分之八；到三万两千，占百分之七十三；到十三万，超过百分之九十。长提示词的首字延迟，主要是被注意力拖慢的。

### S04 decode：卡在显存带宽
- 画面：两组横条表示 decode 一步要读的字节：权重（橙）+ KV cache（紫），分别是 4K 和 32K、batch 16；右侧标出吞吐；下方写算术强度与脊点。
- 屏幕文字：算术强度 ≈ 1.7 次/字节 ≪ H100 脊点 ≈ 295
- 旁白：第二个阶段是 decode，每一步只生成一个 token。为了这一个 token，GPU 要把全部权重读一遍，再把这条对话的整个 KV cache 读一遍。主线模型在 H100 上，每读一个字节只做不到两次运算，而 H100 要每字节做将近三百次运算才能吃饱。所以 decode 快不快，看的是要读多少字节。上下文短的时候，大头是权重，拼一批请求就能共享；到了三万两千，KV cache 比权重还大，而且每条对话各读各的，拼批也省不掉：十六条对话拼一批，吞吐只涨了三成。

### S05 显存装得下几条
- 画面：三根柱子：MHA 10 条、GQA 20 条、若换 MLA 74 条（80 GB、32K 上下文）。
- 屏幕文字：80 GB 能同时服务几条 32K 对话
- 旁白：还有一个更硬的限制：放不放得下。一张 80 GB 的卡，扣掉权重，32K 上下文下主线模型最多同时服务 20 条对话；如果是不共享的 MHA，只有 10 条。KV cache 每小一半，能服务的对话就多一倍，decode 也快将近一倍。这就是第五部分所有架构演进的动机。

### S06 按层记账
- 画面：四行横条随上下文长度 T 从 0 涨到 128K：全注意力线性变长；MLA 也线性但慢得多；滑动窗口涨到窗口就停；线性注意力是一根不动的短条。标注"示意"。
- 屏幕文字：全注意力 · MLA · 滑动窗口 · 线性注意力
- 旁白：今天的模型，层和层已经不一样了，所以账要按层记。全注意力层，每个位置存 K 和 V，随长度线性增长。MLA 层也线性增长，但每个位置存得小得多。滑动窗口层只存最近一段，涨到窗口大小就停。线性注意力层干脆不存 K 和 V，只有一个大小固定的状态。

### S07 公开模型的账本
- 画面：七根横条，128K 上下文的 KV cache；蓝色是纯 GQA，绿色是滑动窗口或混合线性，紫色是 MLA；DeepSeek-V3 旁边注明同头数 MHA 为 488 GiB。底部三条路。
- 屏幕文字：少存头 · 每个位置存更小 · 少存层
- 旁白：拿这个账本去算几个最新的开源模型，数字全部来自它们的配置文件，上下文十三万 token。Qwen3-8B 要 18 GiB。gpt-oss 一半层是 128 的滑动窗口，只要 4.5。Qwen3.5 每四层只有一层全注意力，九十亿参数只要 4 GiB，四千亿参数的版本也只有 3.75。DeepSeek-V3 用 MLA，要 8.6 GiB；如果是同样头数的 MHA，要四百八十多 GiB。省缓存有三条路：少存头，每个位置存得更小，少存层。它们还可以叠加。

### S08 少存头：MHA → GQA → MQA
- 画面：三列，每列上方 8 个查询头（蓝），下方 KV 头（橙）8 个 / 2 个 / 1 个，连线表示共享；下面写缓存比例。
- 屏幕文字：MHA 1×　GQA 1/4　MQA 1/8
- 旁白：先看第一条路：少存头。MHA 里，每个查询头都有自己的 K 和 V。MQA 让所有查询头共用一组，缓存最小，表达能力也最弱。GQA 折中，几个头共用一组。它们的思路是一样的：减少 KV 头的数量。代价是，共用一组的那些头，看到的 key 和 value 完全相同。

### S09 MLA：压成一个潜向量
- 画面：输入 x（长条）经 {W_DKV|W D K V} 压成短条 c_KV（黄框"缓存"），再由每个头自己的 W_UK、W_UV 还原出 k_i、v_i；旁边一小段 k_R 也标"缓存"。
- 屏幕文字：7168 维 → 512 维潜向量 c_KV
- 旁白：第二条路，是 DeepSeek 提出的多头潜在注意力，MLA。它不减少头数，而是先把输入压成一个很小的潜向量，在 DeepSeek-V3 里只有 512 维，缓存里只存它。需要的时候，再用每个头自己的矩阵，把 K 和 V 还原出来。GQA 是硬性规定哪些头共用；MLA 是要求所有头的 K 和 V 都能从同一个小向量算出来，怎么共享，由训练自己学。

### S10 解耦 RoPE 与吸收
- 画面：注意力分数的等式，用括号移动展示 W_UK 并进 query；然后 RoPE 段单独拿出来；最后 576 对 40,960 的对比。
- 屏幕文字：512 + 64 = 576　vs　MHA 40,960
- 旁白：推理时，其实不用真把 K、V 还原出来。注意力分数是 query 乘上 {W_UK|W U K}、再乘潜向量。矩阵乘法满足结合律，可以先把 {W_UK|W U K} 并进 query，让 query 直接和缓存里的潜向量做点积；value 那一侧也一样。这叫吸收。但是 RoPE 会破坏它：位置相关的旋转夹在中间，就没法提前合并。所以 MLA 另拿 64 维专门带位置，所有头共享一份，也要缓存。每层每个位置一共 576 个数，只有同样头数 MHA 的百分之一点四。吸收之后，所有头读的是同一份缓存：训练时像 MHA，推理时像 MQA。

### S11 小实验
- 画面：左边五根横条是每 token 的缓存大小（MHA、GQA、MQA、MLA-48、MLA-16）；右边每种方案三个种子的验证 loss 点和均值线。
- 屏幕文字：同一个小模型，只换注意力，训练 600 步 × 3 个种子
- 旁白：在 CPU 上做个小实验：第十章那个字符级小模型，只换注意力，同样训练六百步，每种跑三个随机种子。EXP_NARRATION

### S12 谁在用，代价是什么
- 画面：左边四个家族（DeepSeek、Kimi、GLM、Mistral）的旗舰模型；右边三条代价；底部结论。
- 屏幕文字：MLA：四家大 MoE 在用；稠密小模型仍用 GQA
- 旁白：写作时，DeepSeek、Kimi、GLM、Mistral 四个家族的旗舰模型都用了 MLA，满足我们的共识标准。但它们全是几千亿参数的大 MoE 模型，稠密小模型几乎都还是 GQA。MLA 有代价：decode 时每个头要在 576 维上做点积，算力更高；它和 QK-Norm 不兼容；还需要专门的 kernel。GLM-5 的报告还发现，在他们的设置下 MLA 起初比不过 GQA，调整了优化器才追平。所以主线模型继续用 GQA。

### S13 从极简到生产级
- 画面：左边极简代码文件，右边生产级文件，箭头相连；下方行业实现；最后出现"下一章：局部与稀疏注意力"。
- 屏幕文字：code/ → zero/tools/kv_cache_calc.py · zero/arch/mla.py
- 旁白：生产级代码里，kv cache calc 能直接读任何模型的配置文件按层记账，测试保证它和真实分配的缓存逐字节相等；zero arch 里的 MLA 可以换进主线的 Transformer，带缓存和不带缓存生成的结果完全一致。真正上线，要用 vLLM 的分页缓存和 FlashMLA 这样的专门 kernel。下一章，我们走第三条路：让一些层只看最近的一段。
