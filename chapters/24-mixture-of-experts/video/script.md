## 二、分镜与旁白

### S01 片头
- 画面：章节标题卡淡入："第 24 章 / 混合专家（MoE）"，副标题"参数翻几十倍，每个 token 的算力不变"。
- 屏幕文字：第 24 章 · 混合专家（MoE）
- 旁白：前几章我们一直在给注意力省钱。这一章换一个地方：前馈网络。今天最大的开源模型，几乎全都是混合专家，也就是 MoE。它们的参数有几千亿甚至上万亿，每个 token 却只用其中一小部分。这是怎么做到的？

### S02 FFN 是大头
- 画面：两根堆叠横条，Qwen3-8B 与主线模型每层的参数：注意力（紫）+ FFN（橙），标出 FFN 占比。
- 屏幕文字：FFN 占每层参数 78%
- 旁白：先看参数都去哪了。千问三 8B 的每一层，注意力只占两成多，前馈网络占了将近八成。每个 token 的计算量，也大致和这些参数成正比。所以想让模型变大，最自然的地方就是 FFN；可 FFN 一变大，每个 token 的计算也跟着变大。

### S03 拆成很多专家，每次只用几个
- 画面：左边一个 token 向量，中间一个路由器方块，右边 8 个专家方块；路由器给每个专家打分，最高的两个亮起，箭头连过去，再汇合到输出。换一个 token 再演示一次，亮起的专家不同。
- 屏幕文字：总参数 ≠ 激活参数
- 旁白：MoE 的办法是：把一个大 FFN 换成很多个小 FFN，叫专家。再加一个很小的路由器，给每个 token 挑几个专家。比如八个专家里挑两个，这个 token 只经过这两个专家，其余六个不参与计算。不同的 token 挑到的专家不一样。于是模型的总参数变成了八份，每个 token 的计算量却只有两份。

### S04 路由公式
- 画面：三行公式逐行出现：打分、选 top-k（带偏置 b）、门控加权求和；旁边标注 sigmoid / softmax。
- 屏幕文字：s = σ(x·W_r)，选 TopK(s + b)，y = Σ g_i·FFN_i(x)
- 旁白：路由器本身就是一个线性层，给每个专家打一个分。DeepSeek 这一派用 {sigmoid|西格莫伊德}，千问、{Mixtral|米克斯特拉尔}、{gpt-oss|G P T O S S} 用 {softmax|软最大}。取分数最高的 K 个专家，把它们的分数归一化成权重，再把这几个专家的输出加权求和。代码里，我们把这个写法和逐个 token 算的朴素版本对了一遍，误差在十的负十六次方。

### S05 真实模型：总参数和激活参数
- 画面：一组横条：每个模型两根，浅色是总参数、深色是激活参数（对数尺度或分两段），模型依次为 Mixtral、Qwen3-235B、GLM-4.5、DeepSeek-V3、Kimi K2、gpt-oss-120b；右侧标注激活比例。
- 屏幕文字：激活比例 3%–28%
- 旁白：看几个真实模型。{DeepSeek|深度求索} V3 总共 6710 亿参数，每个 token 只激活 370 亿，大约百分之六。{Kimi|基米} K2 一万亿参数，激活 326 亿，只有百分之三。{gpt-oss|G P T O S S} 120b 激活不到百分之五。两年前的 {Mixtral|米克斯特拉尔} 是八个专家选两个，激活将近三成。我们按官方配置文件自己数了一遍，和官方公布的数字对得上。

### S06 问题：路由坍缩
- 画面：小实验"MoE-无均衡"第 1 层（从 0 数）的负载直方图（8 根柱子）随训练步数变化，少数柱子越来越高，其余趋近于零；虚线标出均匀负载 1/8。
- 屏幕文字：富者愈富：少数专家包揽大部分 token
- 旁白：可是路由器是训练出来的，这就有一个危险：某个专家一开始分到的 token 稍多一点，它就被训练得更好，路由器就更爱选它，越来越多。在我们的小实验里，不加任何均衡，第一层的第三个专家从百分之二涨到了百分之四十五，第六个专家跌到了零，训练结束也没有回到均衡。闲着的专家白占显存；用专家并行时，最忙的那张卡还会拖慢所有人。

### S07 辅助损失
- 画面：公式 L_aux = α·Σ f_i·P_i；下方 f_i、P_i 的含义；右侧手算小例子：负载 3 比 1，f = [1.5, 0.5]，P = [0.7, 0.3]，L = 1.2α；均衡时 L = α。
- 屏幕文字：L_aux = α · Σ f_i · P_i
- 旁白：传统办法是加一个辅助损失。f 是每个专家实际分到的 token 比例，P 是路由器给它的平均概率，两者相乘再求和。完全均衡时它最小，等于 {α|阿尔法}；哪个专家过载，梯度就压低它的路由概率。问题是，这个梯度和语言模型本身的梯度会互相拉扯：{α|阿尔法} 太小管不住，太大又伤害模型质量。

### S08 无辅助损失：偏置
- 画面：左边 8 根负载柱子（来自 `02_moe_layer.py` 的偏斜路由器），右边 8 个偏置 b 的小刻度；每次更新时过载的 b 下降、欠载的 b 上升，柱子逐渐拉平，显示"更新 0 / 10 / 30 次"和"最大/平均"数值。
- 屏幕文字：b_i ← b_i + γ · sign(平均负载 − 负载_i)
- 旁白：{DeepSeek|深度求索} V3 换了一个思路：给每个专家一个偏置，只在挑专家的时候加到分数上，不参与加权，也不吃梯度。每训练一步，过载的专家偏置减一点，欠载的加一点。这里我们固定一个严重偏心的路由器，什么都不训练，只更新偏置：最忙的专家一开始是平均的四倍，三十次更新后就降到了一点零五。

### S09 容量因子与不丢 token
- 画面：一排专家"桶"，每个桶有容量线；偏斜负载时溢出部分标红（被丢弃 50.3%），均衡后没有溢出。
- 屏幕文字：容量因子 1.25：丢弃 50.3% → 0%
- 旁白：负载均衡还关系到丢不丢 token。早期的 {Switch|斯威奇} {Transformer|传思否么} 给每个专家设一个容量上限，超出的 token 直接跳过这个专家。上面那个偏心的路由器，容量因子一点二五时会丢掉一半的分配；均衡之后一个都不丢。{DeepSeek|深度求索} V3 报告说它训练和推理都不丢 token，前提就是负载足够均衡。

### S10 小实验：负载直方图
- 画面：三组第 1 层的负载直方图并排：无均衡、辅助损失、无辅助损失（训练结束时），标注"最大/平均"；右上角标注"极小实验"。
- 屏幕文字：同一个模型，三种均衡方式
- 旁白：回到小实验。同一个四层的字符级小模型，FFN 换成八个专家选两个，只改均衡方式。不加均衡，最忙的专家是平均的三点六倍；加辅助损失，降到一点零五；用偏置，一点二，而且一百步就拉平了。两种办法都有效，没有闲置的专家。

### S11 小实验：和稠密比
- 画面：横条图：六个方案的验证 loss（均值，误差线为两个种子的范围）：稠密-384（同激活）、稠密-1536（同总参）、三种 MoE、细粒度+共享。
- 屏幕文字：同激活算力 vs 同总参数
- 旁白：再看质量。五个每 token 算力相同的方案，稠密和四种 MoE，验证损失都在一点七八到一点七九之间，差距比换一个随机种子的波动还小。所以这个小实验说明不了谁更好。有意思的是，总参数相同、但算力是四倍的宽稠密模型反而最差：只训练八百步，数据和步数才是瓶颈。MoE 用更多参数换质量，要在上万亿 token 的规模上才兑现。

### S12 细粒度专家 + 共享专家
- 画面：左：粗粒度（8 个大专家选 2）→ 细粒度（64 个小专家选 8）的方块图，组合数从 C(16,2) = 120 变成 C(64,8) ≈ 44 亿；右：两列模型名单：有共享专家（DeepSeek-V3、Kimi K2、GLM-4.5、Llama 4、Qwen3.5、Nemotron 3）/ 没有（Qwen3-MoE、gpt-oss、Mixtral、MiniMax-M2）。
- 屏幕文字：细粒度：更多、更小的专家；共享专家：每个 token 都经过
- 旁白：今天的大模型还有两个共同的变化。一是细粒度：专家更多、更小，每次选得更多。十六个专家选两个只有一百二十种组合，切成六十四个选八个，就有四十多亿种。二是共享专家：留一两个专家让每个 token 都经过，负责大家都要的通用知识。不过这是一条光谱：{DeepSeek|深度求索}、{Kimi|基米}、{GLM|G L M}、{Llama|拉玛} 4、千问三点五都有共享专家；千问三的 MoE、{gpt-oss|G P T O S S}、{Mixtral|米克斯特拉尔} 就没有。

### S13 为什么小模型很少用
- 画面：左：Qwen3.5 产品线：稠密 0.8B、2B、4B、9B、27B | MoE 35B-A3B、122B-A10B、397B-A17B，分界线；右上：Qwen3 报告表 5：30B-A3B ≈ 14B 稠密；右下：batch 1 / 16 / 64 时读取的专家比例 6.2% → 64.4% → 98.4%。
- 屏幕文字：MoE 省的是算力，不是显存
- 旁白：那为什么小模型很少用 MoE？看千问三点五的产品线：27B 以下全是稠密，35B 起才是 MoE。关键是显存装的是总参数。千问三的报告里，30B 总参数、激活 3B 的 MoE，成绩和 14B 的稠密模型差不多：算力省了将近五倍，显存却要多一倍。大集群上算力最贵，MoE 很划算；手机上内存最紧，同样的内存放一个稠密模型更好。所以我们的主线模型保持稠密。

### S14 谁在用，从极简到生产级
- 画面：上半部分：无辅助损失的采用方（DeepSeek、GLM、NVIDIA Nemotron、Kimi、MiniMax、小米 MiMo）与仍用辅助损失的（Qwen3、Llama 4、Mixtral）；下半部分：`code/02_moe_layer.py` → `zero/arch/moe.py` 箭头；最后出现"下一章：多 token 预测与推测解码"。
- 屏幕文字：code/ → zero/arch/moe.py
- 旁白：无辅助损失的偏置均衡，写作时已经被 {DeepSeek|深度求索}、{GLM|G L M}、英伟达的 {Nemotron|尼莫特龙} 在报告里明确采用，{Kimi|基米}、{MiniMax|迷你麦克斯}、小米的配置文件里也能看到，达到了我们的共识标准；千问、{Llama|拉玛} 仍然用辅助损失。生产级代码 zero arch moe 支持两种均衡、共享专家和容量因子，测试保证一个专家时和稠密 {SwiGLU|斯维格鲁} 完全一致。下一章，我们看模型怎么一次预测多个 token。
