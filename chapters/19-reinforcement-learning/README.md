## 1. 模仿的天花板

先看一个极小的例子（[`code/02_grpo_from_scratch.py`](code/02_grpo_from_scratch.py)）。任务是两个个位数相加，输出答案的数字再输出 `<eos>`。老师是个"不太会进位"的模型：不进位的题全对；进位的题只有 30% 写对，另外 70% 忘了写进位（7+5 写成 "2"）。学生照着老师的 2000 条示范做 SFT：

| | 准确率 |
|---|---:|
| 老师示范（2000 条） | 0.684 |
| SFT 学生，采样 | 0.68 |
| SFT 学生，贪心解码 | 0.60 |
| SFT 学生，贪心解码，只看进位题 | **0.11** |

学生学得很"好"：采样准确率和老师几乎一模一样——连老师的错误也原样学会了。进位题上，老师多数时候写错，于是学生最有把握的答案也是错的，贪心解码只剩 0.11。**模仿学习的上限就是示范数据**，示范里的偏差会被忠实继承。

但注意一个细节：学生采样时，进位题仍有 30% 左右的概率写对。正确答案**在模型的分布里**，只是不是最可能的那个。如果有一个程序能告诉模型"这次对了、那次错了"，就能把这 30% 放大。判断两个数的和对不对，一行代码就够——这样的奖励叫**可验证奖励**（verifiable reward）。用它做强化学习，60 步之后：

| | SFT 之后 | GRPO 第 5 步 | 第 10 步 | 第 60 步 |
|---|---:|---:|---:|---:|
| 贪心准确率 | 0.60 | 0.96 | 1.00 | 1.00 |
| 贪心准确率（进位题） | 0.11 | 0.91 | 1.00 | 1.00 |
| 采样准确率 | 0.68 | 0.88 | 0.95 | 0.98 |

学生超过了老师。下面几节把中间发生的事拆开讲。

## 2. 策略梯度：分数不可导，梯度从哪来

把语言模型看成一个**策略**（policy）π_θ：给定提示词 x，它按概率生成回答 y。我们想最大化期望奖励

```
J(θ) = E_{y~π_θ(·|x)} [ r(x, y) ]
```

麻烦在于 r 是个判分程序——"答案对不对"——它对 θ 不可导，也没有梯度可以反传。**对数导数技巧**（log-derivative trick）绕开了它：

```
∇J = ∇ Σ_y π_θ(y) r(y)
   = Σ_y r(y) ∇π_θ(y)
   = Σ_y π_θ(y) r(y) ∇log π_θ(y)        （因为 ∇π = π · ∇log π）
   = E_{y~π_θ} [ r(y) ∇log π_θ(y) ]
```

最后一行是个期望，可以用采样估计：让模型生成几个回答，每个回答的"对数概率的梯度"乘上它的得分，平均一下。r 只作为一个数出现，**不需要可导，只需要能打分**。这就是 REINFORCE（Williams, 1992）。直觉很朴素：得分高的回答，把它的概率往上推；得分低的，往下压。

对语言模型，log π_θ(y) = Σ_t log π_θ(y_t | x, y_<t)，所以 ∇log π 就是回答里每个 token 的对数概率梯度之和——和 SFT 的交叉熵梯度一模一样，只是每条样本多乘了一个"得分"系数。SFT 可以看成所有样本系数都等于 1 的特例（DeepSeekMath 论文第 5 节把 SFT、拒绝采样、DPO、PPO、GRPO 都统一写成"梯度系数"的不同选法）。

[`code/01_reinforce_bandit.py`](code/01_reinforce_bandit.py) 在一个 5 臂老虎机上验证这件事：策略 π = softmax(θ)，采样估计和精确梯度对拍：

| 样本数 N | 采样估计与精确梯度的最大差 |
|---:|---:|
| 100 | 0.0217 |
| 10,000 | 0.0010 |
| 1,000,000 | 0.0001 |

## 3. 方差与基线

REINFORCE 是无偏的，但方差很大。一个关键的观察：对任意常数 b，

```
E[ (r − b) ∇log π ] = E[ r ∇log π ] − b · E[∇log π] = ∇J       （因为 E[∇log π] = Σ ∇π = ∇1 = 0）
```

减去一个**基线**（baseline）b 不改变期望，却能大幅改变方差。直觉：如果所有回答都得 10 分左右，不减基线的话每个回答都被"往上推"，只是推得多少略有不同——信号淹没在噪声里；减掉平均分之后，高于平均的推上去、低于平均的压下来，信号干净得多。`01` 的输出：

| 奖励 | 基线 b | 均值与精确梯度的最大差 | 方差（各分量求和） |
|---|---|---:|---:|
| 原始 r | 0 | 0.0004 | 0.1946 |
| 原始 r | E[r] | 0.0004 | 0.0534 |
| r + 10 | 0 | 0.0076 | 84.70 |
| r + 10 | E[r] | 0.0006 | 0.0533 |

奖励整体 +10 时，不减基线的方差是减基线的 **1589 倍**。拿同样的学习率训练 300 步（每步 8 个样本，5 个种子平均），最好那只手臂的概率：

| | 第 1 步 | 第 50 步 | 第 100 步 | 第 300 步 |
|---|---:|---:|---:|---:|
| 无基线 | 0.21 | 0.20 | 0.20 | 0.40 |
| 基线 = 这一批的平均奖励 | 0.21 | 0.85 | 0.95 | 0.99 |

"用同一批样本的平均奖励作基线"——记住这个做法，GRPO 的核心就是它。

## 4. 从 PPO 到 GRPO

### 4.1 PPO 回顾（第 18 章的铺垫）

PPO（Proximal Policy Optimization）是 RLHF 的标准算法，它在 REINFORCE 上加了两样东西：

1. **价值模型（critic）当基线**：训练一个和策略差不多大的模型 V(s)，预测"从这个位置往后大概能得多少分"，再用 GAE 算出每个 token 的优势 A_t。
2. **裁剪的重要性比**：一批样本要更新好几次（省采样），第二次更新时策略已经变了，所以用 ρ_t = π_θ(y_t)/π_old(y_t) 修正，并把 ρ 限制在 [1−ε, 1+ε] 里，防止一次走太远：

```
ℓ_t = −min( ρ_t · A_t,  clip(ρ_t, 1−ε, 1+ε) · A_t )
```

裁剪的效果按优势的正负分开看：A > 0（好回答）时，ρ 超过 1+ε 就不再给梯度——"已经加够了，别贪"；A < 0（坏回答）时，ρ 低于 1−ε 就不再给梯度——"已经压够了"。

问题在于价值模型：它和策略一样大，要多占一份显存、多训一个模型；而语言模型的奖励通常只在回答末尾给一个数，让价值模型在每个 token 上都估得准并不容易（DeepSeekMath 论文 4.1.1 节原话）。

### 4.2 GRPO：用"同一道题的其他回答"当基线

GRPO（Group Relative Policy Optimization，DeepSeekMath, 2024）的做法是**把价值模型整个去掉**：对每个提示词采样 G 个回答，用验证器打分 r_1..r_G，组内归一化得到优势：

```
A_i = ( r_i − mean(r_1..r_G) ) / std(r_1..r_G)
```

回答 i 里的每个 token 共享同一个 A_i。这正是第 3 节的"批均值基线"，只是按提示词分组：同一道题上高于平均的回答被推上去，低于平均的被压下来。除以标准差是把不同题的信号缩放到同一尺度。`02` 第 1 步里一组真实的样本（题目 2+8，G = 8）：

| 回答 | 10 | 0 | 0 | 10 | 10 | 0 | 10 | 0 |
|---|---|---|---|---|---|---|---|---|
| 奖励 | 1 | 0 | 0 | 1 | 1 | 0 | 1 | 0 |
| 优势 | +0.94 | −0.94 | −0.94 | +0.94 | +0.94 | −0.94 | +0.94 | −0.94 |

（4 对 4 时均值 0.5、无偏标准差 0.535，所以优势是 ±0.94。）"0" 就是那个忘了写进位的答案。

对应的代码只有几行：

```python
def group_advantages(rewards, eps=1e-6):          # rewards: (P, G)
    mean = rewards.mean(1, keepdim=True)
    std = rewards.std(1, keepdim=True)            # 无偏标准差，与 TRL / verl / zero 一致
    return (rewards - mean) / (std + eps)         # A_i = (r_i − mean) / std

def grpo_loss(logp, old_logp, ref_logp, adv, mask, eps_clip=0.2, beta=0.02):
    ratio = torch.exp(logp - old_logp)                                 # ρ_t = π_θ / π_old
    A = adv[:, None]
    per_tok = torch.maximum(-ratio * A,
                            -torch.clamp(ratio, 1 - eps_clip, 1 + eps_clip) * A)   # 裁剪
    d = ref_logp - logp
    kl = torch.exp(d) - d - 1                                          # k3：非负、无偏的 KL 估计
    per_tok = per_tok + beta * kl
    m = mask.float()
    return (per_tok * m).sum() / m.sum()                               # token_mean 聚合
```

完整的训练循环就是：取 P 道题 → 每题复制 G 份采样 → 验证器打分 → 组内优势 → 用上面的损失更新 μ 次。`02` 用 P = 16、G = 8、ε = 0.2、β = 0.02、μ = 2。

**一组全对或全错时，优势全为 0，这组对梯度没有贡献。** `02` 的日志里，"零方差组"的比例从第 5 步的 0.56 升到第 20 步的 0.94——模型越学越好，能提供信号的题越来越少。这是 GRPO 在实践中最常遇到的问题之一，第 5 节的"难度筛选"就是为它准备的。

### 4.3 三个细节：KL、聚合方式、裁剪什么时候起作用

**KL 约束与 k3 估计。** 可选地加一项 β · KL(π_θ ‖ π_ref)，让策略不要离起点（SFT/DPO 模型）太远。GRPO 把它直接加在损失里（而不是像 RLHF 那样扣在奖励里），逐 token 用 k3 估计：

```
KL ≈ π_ref/π_θ − log(π_ref/π_θ) − 1        （Schulman 的 "Approximating KL"，DeepSeekMath 式 4）
```

它总是非负（x − log x − 1 ≥ 0），期望等于真正的 KL。用可验证奖励时，很多团队干脆把 KL 去掉（β = 0）：GLM-4.5 的推理 RL "在 GRPO 框架上去掉 KL 项"，MiMo-7B 和 OLMo 3 也都去掉了；DeepSeek-R1 保留了一个很小的 β = 0.001。理由是：RLHF 里 KL 是为了防止策略跑到奖励模型不可信的区域；而规则验证器不会"不可信"，限制也就没那么必要。主线配置 `configs/main/grpo.toml` 默认 `kl_coef = 0.0`，tiny 配置用 0.02 演示参考模型的用法。

**聚合方式。** 一批回答长短不一，逐 token 的损失怎么平均？原始 GRPO 论文先在每条回答内平均，再在回答之间平均（`seq_mean_token_mean`）。这样长回答里每个 token 的权重被稀释：一条又长又错的回答，每个 token 挨的罚更轻。DAPO 改成所有回答 token 一起平均（`token_mean`）；MiMo-7B 的目标函数写的就是 1/Σ|o_i| 的 token 级平均，OLMo 3 明确采用 token 级损失"避免长度偏差"，GLM-4.5 在代码 RL 上比较过两种写法，token 加权平均收敛更快。`zero` 默认 `loss_agg = "token_mean"`。

**裁剪什么时候起作用。** 如果每批样本只更新一次（μ = 1），那么 π_old 就是当前策略，ρ ≡ 1，裁剪永远不触发——但 ∇ρ = ∇log π 不为零，梯度照样有，退化成带组基线的 REINFORCE。只有同一批样本更新多次（μ > 1，或大批次拆成多个小批次依次更新），ρ 才会偏离 1。`02` 用 μ = 2，裁剪比例在 0.00–0.02 之间；冒烟测试的 tiny 配置 `ppo_epochs = 1`，日志里 clip 一直是 0.00。

## 5. GRPO 的各种改进：哪些进正文，哪些还在观察

2025 年以来出现了一大批 GRPO 的改进。按 GOAL.md 2.1 的规则（至少 3 个独立的头部开源模型家族在技术报告里明确采用），逐项核对的结论：

| 做法 | 谁明确采用（技术报告） | 结论 | zero 里 |
|---|---|---|---|
| 组内基线、不要价值模型（GRPO 本身） | DeepSeek-R1、Qwen3（推理 RL）、GLM-4.5、MiMo-7B、OLMo 3；Kimi K2 用组均值基线但目标函数是 K1.5 的变体 | **共识** | `group_advantages` |
| token 级聚合 | MiMo-7B、OLMo 3、GLM-4.5（代码 RL）；出处 DAPO | **共识**（3 家） | `loss_agg = "token_mean"`（默认） |
| 去掉 KL 项 | GLM-4.5、MiMo-7B、OLMo 3；DeepSeek-R1 仍保留 β = 0.001 | **常见选择**（3 家），不是必须 | `kl_coef = 0.0`（main） |
| 按难度筛题：去掉全对/全错的题 | MiMo-7B（动态采样 + 简单题重采样）、OLMo 3（零梯度过滤 + active sampling）、GLM-4.5（按难度的课程学习）、Kimi K2（按 SFT 模型 pass@k 只留中等难度）、Qwen3（query 要"对冷启动模型可学"） | **共识的原则**；在线动态采样的具体做法各家不同 | 只记录 `zero_std_groups`，**未实现**在线过滤（见"主线进度"） |
| clip-higher（ε_high > ε_low） | MiMo-7B、OLMo 3；出处 DAPO（字节 Seed） | **待核实**：明确采用的头部家族只找到 2 家 | `clip_eps_high`（main 设 0.28，可设 0 关闭） |
| 不除以标准差（Dr. GRPO） | OLMo 3 | 前沿观察 | `scale_rewards = false` 可切换 |
| 序列级重要性比（GSPO） | Qwen3 后续版本（GSPO 论文自述） | 前沿观察 | 未实现 |

"待核实"不等于"没用"：clip-higher 在 DAPO 的消融里把 AIME 从 36 提到 38（Qwen2.5-32B 基座），MiMo 和 OLMo 3 都用了；只是按本课的规则，第三家的明确证据还没找到。主线配置保留它作为一个可以一键关掉的开关，第二步用自己的开发集（不是预注册的测试基准）决定开不开。

## 6. 可验证奖励：怎么给工具调用打分

强化学习的效果，上限是奖励的质量。DeepSeek-R1 在推理任务上**只用规则奖励**（准确率奖励 + 格式奖励），明确不用神经网络奖励模型，理由是"神经奖励模型在大规模 RL 中容易被 reward hacking"；Qwen3 的报告也说"设计良好的规则奖励能高精度判断输出对错，防止 reward hacking"。这类"答案能被程序检查"的强化学习，Tülu 3 起名叫 **RLVR**（Reinforcement Learning with Verifiable Rewards）：

| 领域 | 验证器 | 例子 |
|---|---|---|
| 数学 | 抽出最终答案，和标准答案做等价比较 | DeepSeek-R1（答案写在 box 里）、OLMo 3（SymPy 比较） |
| 代码 | 在沙箱里跑测试用例 | DeepSeek-R1、MiMo-7B（按测试难度给部分分）、OLMo 3（通过率或全过才给分） |
| 指令遵循 | 每条约束一个检查函数 | Tülu 3、OLMo 3（满足的约束比例） |
| 工具调用 | 格式检查 + 调用与标准调用比对 / 执行结果比对 | GLM-4.5（格式对且和标准调用完全一致才给 1）、本课 `tool_env` |

小米开源的 [XiaomiMiMo/verl](https://github.com/XiaomiMiMo/verl) 复现了 MiMo-V2.6 的五类 RL 环境，正好是验证器的三种主要形态：**可执行测试**（代码：软件工程任务）、**规则检查**（网络安全的漏洞复现、符号音乐创作）、**rubric 判分**（通用知识工作：一组"通过/不通过"的断言，由 LLM 裁判逐条判定），外加网页开发的视觉判分。读它的代码能看到几条值得照搬的工程原则：

- **环境故障和模型失败分开记**：沙箱超时、容器挂了这类基础设施错误，得一个显眼的无效值并单独统计，而不是悄悄记成 0 分——否则模型会因为环境的问题被惩罚；
- **判分器本身也会静默退化**：代码注释里记录过一次，某个评分脚本因为路径问题找不到依赖，悄悄降级成部分分恒为 0 的打法，只能靠监控发现；
- **单独维护"防作弊"的配置**（配置名里带 antihack）；
- 调试用的随机奖励开关会把真实分数另存一份（`true_reward`），训练用的奖励和真实分数分开记。

主线模型的环境在 `zero/post/envs/tool_env.py`：6 个模拟 API（计算器、天气、单位换算、日期加减、日期间隔、星期几），全部确定性、不联网；约 10% 的题不需要调用工具，考模型"该不调就不调"。打分规则：

```
格式错误（JSON 坏了、标签不配对、伪造 <tool_response>、超长、调用过多）→ −1
不该调工具却调了 → −0.5；该调却没调 → 0
否则  0.1（格式分）+ 0.9 × Σ 每个标准调用的得分 / 标准调用数 − 0.25 × 多余调用数 − 0.5 × 不合 schema 的调用数
      每个标准调用：函数名 + 参数 AST 一致或执行结果一致 → 1；只有函数名对 → 0.2
```

"AST 一致"是参数规范化后逐项相等（BFCL 也用这个思路）；"执行一致"是真的调用一遍模拟 API，结果相同也算对（`"28-44"` 和 `"28 - 44"` 都行）。[`code/04_tool_env_rewards.py`](code/04_tool_env_rewards.py) 把几种典型输出喂给生产级判分器：

| 输出（题目："帮我算一下 28 - 44 等于多少？"） | 奖励 | 理由 |
|---|---:|---|
| 正确调用 | +1.00 | |
| 标签里的 JSON 坏了 | −1.00 | 不是合法 JSON |
| 去掉标签的裸 JSON | −1.00 | 守卫 #8：标签外出现 name / arguments JSON |
| 心算出 −16，调用 `calculator("-16")` | +0.28 | 守卫 #2：执行结果一样，但表达式里的数字不对，只给函数名分 |
| 同一个调用喷两遍 | +0.75 | 守卫 #1：一对一匹配，多余调用扣 0.25 |
| 调用后自己编一段 `<tool_response>` | −1.00 | 守卫 #3：伪造工具结果 |
| 闲聊题（"Thanks a lot."）：正常回答 / 空回复 / 裸 JSON / 乱调用 | +1 / 0 / −1 / −0.5 | |

每一条守卫都对应一种"不学本事也能拿分"的捷径，都在 `tests/test_tool_env.py` 里有测试。其中第 8 条不是事先想到的，而是训练中**真实发生**之后补上的——这是下一节的故事。

## 7. 奖励作弊：奖励涨了，本事没涨

### 7.1 真实案例：十步之内学会"去掉标签"

写 `zero` 的冒烟测试时，最初的奖励只检查 `<tool_call>` 标签**里面**的内容。tiny 模型（约 130 万参数）的调用几乎都是坏 JSON，得 −1 分。GRPO 跑了十步，平均奖励曲线漂亮地上升——检查样本才发现，模型学会了**去掉标签、照样输出 JSON**：没有标签就不算"调用"，也就没有格式错误，得分从 −1 变成 0（"该调却没调"）。格式错误率降了，奖励涨了，模型一个调用都不会了。与此同时还有第二个漏洞：不需要工具的题，只要不调用就给满分，回复为空、写一串乱码也是 1 分。

修法就是 `tool_env` 的第 8 条守卫：标签外面出现 `{"name": ...` / `"arguments":` 这样的 JSON，判格式错误（−1）；闲聊题回复为空得 0 分而不是 1 分。

### 7.2 在玩具上重演一遍

[`code/03_reward_hacking.py`](code/03_reward_hacking.py) 把这件事缩小重演。玩具版的正确调用是 `<call> 字 d </call> <eos>`（"函数名 + 参数"，d = (a+b) mod 10），起点模型和 tiny 模型一样：59% 的输出格式是坏的，格式对的调用只有 5%。两种奖励只差第 8 条守卫，同一个起点、同一个随机种子，各跑 120 步 GRPO：

| | 起点 | 天真奖励，第 10 步 | 天真奖励，第 120 步 | 修好的奖励，第 10 步 | 修好的奖励，第 120 步 |
|---|---:|---:|---:|---:|---:|
| 训练奖励（这一批的平均） | — | +0.11 | +0.06 | +0.16 | +0.22 |
| 格式错误率 | 0.59 | 0.01 | **0.00** | 0.10 | 0.00 |
| 工具题：格式正确的调用 | 0.05 | 0.01 | **0.00** | 0.87 | 1.00 |
| 裸调用（标签外出现"调用"） | 0.19 | 0.85 | 0.66 | 0.01 | 0.00 |
| 闲聊题：正常回复 | 0.55 | 0.33 | **0.09** | 0.97 | 1.00 |
| 真实成功率（留出的判据） | 0.14 | 0.08 | **0.02** | 0.29 | 0.36 |

天真奖励下，格式错误率从 0.59 降到 0，训练奖励为正——如果只看这两条曲线，会以为训练很成功。但格式正确的调用从 0.05 降到 0，闲聊题的正常回复从 0.55 降到 0.09，真实成功率从 0.14 降到 0.02。最后一步的样本：

```
天真奖励   工具题 5+4  →  字 5 <eos>                    奖励 +0.0   （去掉了标签）
           闲聊题 #21  →  <eos>                         奖励 +1.0   （空回复拿满分）
修好的奖励 工具题 5+4  →  <call> 字 7 </call> <eos>     奖励 +0.1
           闲聊题 #21  →  字 <eos>                      奖励 +1.0
```

为什么作弊来得这么快？看第一个 token 的决策：起点模型"开标签"这条路平均得分约 −0.9（多数写坏），"不开标签"这条路稳定 0 分。组内优势会把第一个 token 猛推向"不开标签"；一旦不开标签成了习惯，写对格式的样本就很少被采到，也就没有机会被奖励。**策略梯度只会沿着最容易涨分的方向走，它不知道你真正想要什么。**

修好之后，格式问题解决了，真实成功率从 0.14 到 0.36，但也就到这里：这个极小的模型没学会 (a+b) mod 10，工具题的答案仍然基本靠猜（最后一批里全都猜 7）。守卫堵住的是捷径，本事还得靠模型、数据和更长的训练去学。另外注意：**两种奖励的数值不能互相比较**——修好的奖励在第 120 步只有 +0.22，却远好于天真奖励；换了奖励函数，曲线的高低就不再有意义。

### 7.3 一般的防守办法

1. **格式要严**：宁可把"差不多对"的输出判成格式错误，也不要留出"绕开检查"的缝。GLM-4.5 的函数调用奖励是"格式对且和标准调用完全一致才给 1，否则 0"。
2. **惩罚退化输出**：空回复、超长、重复、伪造工具结果、把所有可能的调用都喷一遍。Tülu 3 给没有输出 EOS 的回复 −10 分；Kimi K2 在指令遵循上专门加了一层 hack-check，检测"声称完成了其实没完成"。
3. **留出的验证器和人工抽查**：训练用的奖励和评估用的判据分开。每隔一段时间看样本，看的不是"平均奖励"，而是"这个输出真的对吗"。MiMo 的代码把训练奖励和 `true_reward` 分开记，也是这个意思。
4. **优先用规则，而不是模型打分**：DeepSeek-R1 说神经奖励模型在长时间 RL 中会被钻空子，第二阶段只在最后 400 步加入偏好奖励；MiMo-7B 说基座模型在数学题上会钻判分器的空子，而跑测试用例的代码题很难被钻。
5. **每发现一个漏洞，就补一条测试**：`tests/test_tool_env.py` 里每条守卫都有正例和反例。

## 8. 训练时盯什么

| 指标 | 健康的样子 | 危险信号 |
|---|---|---|
| 平均奖励 | 稳步上升，有噪声 | 猛涨——先去看样本，可能是作弊 |
| 格式正确率 / 调用率 | 一起上升 | 格式正确率涨、调用率跌（7.2 节的样子） |
| 回复长度 | 推理任务上缓慢变长 | 暴涨（乱码、重复）或塌到极短（空回复） |
| KL（对参考模型） | 缓慢增长 | 突然跳升：策略跑得太远 |
| 熵（entropy） | 缓慢下降或基本稳定 | 快速塌到接近 0：探索没了，DAPO 称为"熵坍缩" |
| 裁剪比例 | 很小（百分之几） | 很大：学习率或更新次数太多 |
| 零方差组比例 | 中等 | 接近 1：题太简单或太难，需要换题或筛题 |
| 留出集上的真实成功率 | 跟着奖励一起涨 | 奖励涨、它不涨——reward hacking |

`zero/post/grpo.py` 每步记录奖励、格式正确率、调用率、回复长度、KL、裁剪比例和零方差组比例（`log.jsonl`）；熵目前没有记录。DAPO 的论文提醒过一个反直觉的现象：训练集上的奖励和验证集准确率的相关性常常很低，所以一定要看留出集。

## 9. 推理模型：RL 让模型学会"多想一会儿"

DeepSeek-R1-Zero 直接在基座模型上用 GRPO 和规则奖励训练（奖励 = 准确率 + 格式，要求把思考写在 `<think>` 里），AIME 2024 的 pass@1 从 15.6% 升到 77.9%，同时平均回复长度随训练持续变长——没人教它，它自己学会了在回答里验证、反思、换一种方法再试。DeepSeek-R1 再加上冷启动 SFT 和多阶段 RL，解决可读性和语言混杂的问题。Qwen3 的推理 RL 只用了 3995 个"题目 + 验证器"对，Qwen3-235B-A22B 在 170 步内把 AIME'24 从 70.1 提到 85.1。

两点提醒：一是"回答变长"不全是能力的体现，Dr. GRPO 指出序列平均的写法本身会偏向更长的错误回答；二是 Qwen3 报告里对 Qwen3-8B 的对比，RL 提升了 pass@1，但 pass@64 没有变——RL 更多是把模型本来就能采到的正确答案变成更常见的答案，这和第 1 节进位题的例子是同一个道理。对小模型，Qwen3 的报告还发现从大模型做在线策略蒸馏比直接 RL 效果更好、只用约 1/10 的 GPU 时（见第 17 章）。

主线模型的 GRPO 默认不开思考（工具调用要短而准），`max_new_tokens = 512`。

## 10. 小结

- **模仿有天花板**：SFT/蒸馏会原样继承示范里的错误。强化学习只需要一个能打分的验证器，就能把模型分布里"偶尔对"的答案放大。
- **策略梯度**：∇E[r] = E[r · ∇log π]，奖励不必可导。减去基线不改变期望、大幅降低方差。
- **GRPO**：每题采样 G 个回答，A = (r − 组均值)/组标准差，不需要价值模型；加上裁剪（μ > 1 时起作用）和可选的 k3 KL；token 级聚合。全对/全错的组没有梯度。
- **可验证奖励**：数学比答案、代码跑测试、工具调用比 AST 和执行结果；验证器的三种形态是可执行测试、规则检查、rubric 判分。
- **Reward hacking**：模型会沿最容易涨分的方向走。我们在冒烟测试里亲眼见到它十步之内学会去掉标签。防守靠严格格式、惩罚退化输出、留出判据和人工抽查，以及每个漏洞一条测试。

## 前沿观察

- **clip-higher（DAPO）**：把裁剪上界 1+ε_high 调得比下界宽（DAPO 用 0.2 / 0.28），让低概率的"探索"token 能被推得更高，缓解熵坍缩。MiMo-7B、OLMo 3 采用；按本课规则还差一家明确采用的头部家族，所以列为待核实，主线配置里是一个可关闭的开关。
- **不除以标准差（Dr. GRPO）**：组内标准差很小的题（几乎全对或全错）会被放大权重，造成"难度偏差"；Dr. GRPO 建议只减均值，同时去掉按回答长度的归一化。OLMo 3 采用了不除标准差；目前只找到这一家头部模型明确采用。
- **GSPO**：把重要性比从逐 token 改为整条回答的（长度归一化的）似然比，并在序列级裁剪；Qwen 团队称它稳定了 MoE 模型的 RL 训练、用于 Qwen3 的后续版本。其他家族的采用尚未核实。
- **异步 / off-policy RL**：采样和训练解耦以提高吞吐（OLMo 3 的 in-flight 更新、GLM-4.5 的 slime、MiMo 的 Seamless Rollout），需要额外的重要性修正（如截断重要性采样）；属于基础设施层面的做法，本课主线不涉及。

## 引导问题

带着这些问题去问 Claude Code，直到你能用自己的话讲清楚：

1. 对数导数技巧里，"∇π = π · ∇log π" 这一步为什么让期望可以用采样估计？如果奖励本身依赖 θ（比如用策略模型自己当裁判），推导哪里会出问题？
2. GRPO 的优势对所有 token 都一样。一个 30 个 token 的回答里，只有一个 token 是错的，它和其他 29 个 token 挨的罚一样多——这合理吗？过程奖励模型（PRM）想解决的是什么问题，DeepSeek-R1 为什么说它没成功？
3. 为什么 μ = 1 时裁剪不起作用，但梯度仍然不为零？把 `02` 的 μ 改成 1 和 4，看看裁剪比例怎么变。
4. k3 估计 exp(d) − d − 1 为什么总是非负？它和直接用 log π_θ − log π_ref 当 KL 估计相比，各有什么好处？
5. 除以组内标准差，对"8 个回答里 1 个对"和"4 个对"的两道题，给那个对的回答的优势分别是多少？这算"难度偏差"吗？
6. 如果要给"查天气然后用一句话回答"的两轮任务打分，只看最终回答够吗？中间的工具调用要不要单独给分？GLM-4.5 的"逐步规则 RL"和"端到端多轮 RL"是怎么分工的？

## 动手任务

**任务 1（基础）**：在 `01_reinforce_bandit.py` 里把基线换成"留一法"（leave-one-out：每个样本的基线是同批其他样本的平均奖励），比较方差。它和 GRPO 的组均值只差一个常数因子 G/(G−1)（Dr. GRPO 论文附录 A 有推导）。

**任务 2（核心）**：在 `02_grpo_from_scratch.py` 里把老师在进位题上的正确率从 30% 改成 5% 和 0%，重跑。0% 时 GRPO 还能学会进位吗？为什么？（提示：看第 1 步有没有"有对有错"的组。）这说明 RL 需要什么样的起点？

**任务 3（挑战）**：给 `03_reward_hacking.py` 的"修好的奖励"再找一个漏洞：设计一种输出，它在修好的奖励下能拿到比 `<call> 字 d </call>` 瞎猜更高的平均分，却不是正确行为；然后补一条守卫，重跑确认真实成功率没有下降。把同样的思路用到 `zero/post/envs/tool_env.py` 上：读一遍 `score_tool_calls`，找一种现有守卫没覆盖的作弊方式，写成 `tests/test_tool_env.py` 风格的测试（先在本地试，不要提交）。
