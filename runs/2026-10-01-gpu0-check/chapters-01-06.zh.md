### 细节 3：第 5 章 `03_train_classifier.py` 对照 3（影响正文论证）

README 第 5 节的表格与本机输出（输出层 std = 10，lr = 1.0）：

| 步数 | CE 准确率（README / 实测） | MSE 准确率（README / 实测） |
|---:|---:|---:|
| 0 | 30.7% / 30.7% | 30.7% / 30.7% |
| 100 | 85.7% / 85.7% | **65.3% / 53.3%** |
| 500 | 97.3% / 97.3% | **65.3% / 96.7%** |
| 800 | 98.0% / 98.0% | **66.0% / 99.3%** |
| 1000 | 99.0% / 99.0% | **95.3% / 99.3%** |
| 3000 | 99.3% / 99.3% | **99.3% / 99.0%** |
| 500 步时 p(正确) < 1% 的样本 | 0 / 0 | **103 / 7** |

CE 列逐位一致，MSE 列完全不同。README 的两句话在本机上不成立："MSE 版在 65% 附近卡了七八百步"和"MSE 版有 103 个样本自信地错着"。本机的 MSE 版 500 步就到了 96.7%，800 步时反而比 CE 版高。

排查：

- 换 OpenBLAS 线程数（1 / 4 / 默认 128）：结果不变（本机上的运行是确定性的）。
- 关掉 NumPy 的 AVX2/FMA3 SIMD（`NPY_DISABLE_CPU_FEATURES`）：结果不变。
- 换 OpenBLAS 内核（`OPENBLAS_CORETYPE=Prescott`）：MSE 轨迹又大变（100 步 94.0%，500 步 97.0%，800 步 98.7%；500 步时 < 1% 的样本有 3 个）。`Haswell` 内核的结果与默认相同。

结论：这条 MSE 训练轨迹对矩阵乘法的舍入极其敏感。logits 很大时，softmax 饱和，把 MSE 的梯度压得很小。这时微小的舍入差就能决定哪些样本先"翻过来"。README 的数字多半来自另一种 CPU 或 BLAS 内核，不是代码 bug。

但是，**正文用来支撑论点的具体现象"MSE 卡住七八百步"不可复现**。视频里也写着"65%、103 个"：在 `video/script.md` 的事实 F8 和分镜里。（`scenes.py` 在渲染时由代码实时算曲线，所以画面上的曲线会和旁白对不上。）第 5 节第 4 部分那张"CE vs MSE 梯度大小"表只用公式、不训练，它完全一致。核心论点"模型自信地错时，MSE 的梯度消失"本身没有问题。

**需要你决定**：是否换一个在各种 BLAS 内核下都稳定的演示？例如取多个种子的中位数，或者把 out_std / 学习率调到 MSE 一定会卡住的区间。然后同步修改 README 和视频旁白。我没有改任何文件。

### 重要发现：GPU0 的功耗上限是 240 W（出厂默认 350 W）

`nvidia-smi -i 0` 的结果：`power.limit 240 W, power.default_limit 350 W, clocks.max.sm 2100 MHz`。探针（`scratchpad/ch01-06/probe/clock_probe.py`）连续跑约 4 s 的大矩阵乘法：

| 负载 | 持续 TFLOPS | 采样的 SM 频率 / 功耗 |
|---|---:|---|
| 2048 float32 | 13.0 | 810–960 MHz / 225–239 W |
| 8192 float32 | 15.6 | 960–1020 MHz / 182–240 W |
| 8192 BF16 | 47.4 | 1200–1470 MHz / 158–238 W |

所以在这张卡上，持续满载时功耗顶在 240 W。这时频率只有空闲 boost 频率（约 1.7 GHz）的一半多。基准脚本里 2048 比 4096/8192 快，原因是它每轮只有十几毫秒，还跑在 boost 频率上。

**这会影响所有章节 GPU 实测的绝对数字**，尤其是持续几秒以上的计时。建议主流程在各章 GPU 小节或汇总里统一说明。也可以决定是否把功耗上限恢复到 350 W，然后重测。我没有改动任何 GPU 设置。第 2 章 README 的新小节已经写明了这一点。

第 1、3–6 章的脚本都是 NumPy / 单线程 PyTorch 的小例子，参数从几十到几万个。正文讨论的是数值和收敛，不是速度。把它们放到 GPU 上，只会重复第 2 章"小矩阵 GPU 更慢"的结论。按"宁缺毋滥"的原则，没有加。

考虑过、但放弃了一个候选：第 5 章"从极简代码到生产级代码"里说"autocast 会把 cross_entropy 提升到 float32"。这个说法可以在 CUDA 上验证。但它不在速读正文里，也不改变讲解，所以没做。
