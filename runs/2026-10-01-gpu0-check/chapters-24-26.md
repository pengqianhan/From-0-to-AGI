### 第 24 章：`chapters/24-mixture-of-experts/code/05_gpu_moe.py`（GPU0 上 6 s）

一次 8192 个 token、d = 1024、专家宽 2048、top-2，E = 8 → 128；对比 `02` 的按专家循环与"排序分段 + `F.grouped_mm`"，并和同算力稠密 SwiGLU 比。README 新增 `## GPU 实测（单张 RTX 3090）` 一节（紧挨 `## 从极简到生产级` 之前），表格数字来自 `gpu_24_final.log`：

|---:|---:|---:|---:|---:|---:|---:|---:|
| 稠密 4096 | 13M | 0.0252 | — | — | 4.27 | — | 48.3 |
| 8 | 50M | 0.0252 | 2048 | 6.45 | 6.03 | 1.1× | 34.2 |

**与正文 GPU 说法有关的发现（没有改正文，请主流程决定）**：第 9 节写"GPU 上的做法是 grouped GEMM（一次 kernel 算一组形状不同的矩阵乘）"。profiler 显示 PyTorch 2.11 的 `F.grouped_mm` 在 3090（sm86）上发出 129 个 kernel，其中 128 个是逐专家的 cuBLAS GEMM（`ampere_bf16_s16816gemm…`），不是单个 kernel。正文的概念描述没错，但读者如果在消费级卡上用 PyTorch 的 grouped_mm，拿到的不是"一次 kernel"。README 的 GPU 小节已如实写明。

我起初还测了"解码时每步读多少专家"（对照第 8 节第三笔账），但因为上面这点，`F.grouped_mm` 在 batch 1 时也要 2.2 ms（比把 128 个专家拼成一个稠密 FFN 读一遍的 1.8 ms 还慢），测不出"只读被选中的专家"，所以没有放进最终脚本和 README。

### 第 25 章：`chapters/25-mtp-speculative-decoding/code/06_gpu_speculative.py`（GPU0 上 96 s，约 10 GB 显存）

三部分：① 已有 200 个位置 KV cache 时一次喂 T 个 token 的耗时（本章 0.86M 目标 + 同结构放大的 4.15B 目标，BF16 随机权重）；② 本章训练好的目标 + 草稿在 GPU 上跑 `02` 的 `speculative_greedy`，检查逐字相同并记录逐轮接受数；③ 放大版目标 + 1/322 大小的放大版草稿按真实逐轮接受数"回放"推测解码（前 2 段提示词、3 次中位数），测墙钟加速比，和公式对照。README 小节数字来自 `gpu_25_final.log`：

- T = 1 / 2 / 4 / 8 / 16 / 64 / 256：放大版 13.385 → 14.597 ms（T = 16 时 1.09×），64 时 1.51×，256 时 3.50×；T = 1 有效带宽 621 GB/s。本章小目标在 GPU 上 3.84 ms、平的，但只折合 0.9 GB/s（kernel 下发开销，每个约 6.5 µs）。
- GPU FP32 下 k = 1、2、3、4、6、8 全部逐字相同；α 0.702–0.723（与本机 CPU 复现完全相同）。
- 回放：c ≈ 0.078；k = 1 / 2 / 3 / 4 / 6 / 8 实测 1.61 / 1.90 / 2.18 / **2.25** / 2.18 / 2.01×，公式 1.60 / 1.89 / 2.15 / 2.20 / 2.15 / 2.01×，差距 < 3%。

**与正文 GPU 说法有关的发现（没有改正文，请主流程决定）**：

1. **证实**第 1、5、8 节"decode 受带宽限制，验证 k+1 个位置和生成 1 个差不多"：4.15B 模型 T ≤ 16 时只慢 ≤ 9%。
2. **证实**第 5 节"CPU 小实验的加速比不代表 GPU 上的情况"：GPU 上验证免费、c 小，公式几乎完全吻合，最优 k = 4 时 2.25×（CPU 最多 1.28×）。
3. **部分反驳**第 5 节"真实的 GPU 系统上，草稿通常比目标小两个数量级，c 能到 0.05 以下"：草稿参数是目标的 1/322，但 c = 0.078（时间比约 1/13），因为 eager PyTorch 下草稿的一步几乎全是 kernel 下发开销，c 由层数 / 算子数决定而不是参数量。在用 CUDA Graph / 融合 kernel 的推理引擎里 c 可以更低，但本脚本没有测到 < 0.05。
4. 第 3 节关于"GPU 上不同 batch 大小的数值差异可能导致输出不完全一致"：本次 FP32 GPU 运行没有遇到翻转（6 个 k 全部逐字相同），与正文不矛盾。
5. 顺带：本章小模型在 GPU 上一次前向（3.84 ms）并不比 README 第 1 节单线程 CPU（3.55 ms）快。

另外，GPU 小节里"接受率和第 5 节的表差 0.01–0.02"这句解释了为什么 GPU 的 α 与第 5 节表不同（权重是本机重训的），如果主流程决定用本机结果刷新第 5 节，这句要一起删掉。
