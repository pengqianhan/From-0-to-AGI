### 不一致的共同原因：跨机器的浮点差异（已排除本机不确定性）

所有训练类的不一致（12/03、12/04、13/06、13/07、15/03、15/04）都是同一种形态：固定了种子、`set_num_threads(1)`、代码和数据在 README 提交之后没改过（token 数、文档数等确定性的量都逐位相同），但训练 loss 在第 3–4 位上分叉，高学习率的运行分叉得最厉害，一部分运行则逐位相同。

为了区分"本机每次跑都不一样"和"换了机器才不一样"，我在同一台机器上用 `--fresh` 重跑了一次 `12/03_lr_sweep.py`：两次输出（去掉计时）**逐字节相同**。所以这些脚本在同一环境里是确定的，README 的数字多半来自另一台机器或另一套 CPU 内核（例如不同的指令集 / BLAS），微小的舍入差异被几百到上千步的训练放大。14/04 也印证了这一点：用 `ATEN_CPU_CAPABILITY=default` 重跑，`128×32` 一格的 SDPA 最大差从 8.0e-16 变成 7.8e-16，其余不变——同一段代码换内核，舍入噪声就会变。

**建议**：正文里训练类的数字要么按本机重跑后更新，要么注明"不同机器上第 3 位起会不同"，并把依赖具体数值的定性结论（见细节 2、3、5）改成对这种漂移不敏感的说法。由主流程决定，我没有改。

## 三、GPU 结果与 README 估算的对比要点

1. **混合精度**：3090 上 BF16 矩阵乘最高 60.4 TFLOPS（规格 71 的 85%），FP32 16.9（规格 35.6 的 48%），BF16 快 3.6 倍；训练一步（T = 1024）BF16 比 FP32 快 2.7 倍。BF16 与 FP64 的相对误差 2.9e-3，FP16 3.6e-4（差 8 倍 = 尾数差 3 位）。02 ⑥ 的同一个 Linear：CPU 2.78e-3（与正文一致），GPU 3.25e-3；关掉 cuBLAS 的 `allow_bf16_reduced_precision_reduction` 后 GPU 也是 2.78e-3。
2. **注意力**：朴素写法峰值显存约为 S + P 理论值的 2 倍、随 T 平方增长，T = 16K 放不下；FlashAttention 线性增长（T = 16K 时 514 MiB），快 3.1–5.4 倍。
3. **SDPA 后端**：BF16 下 zero 的 GQA 注意力（`enable_gqa=True`）调用的是 `pytorch_flash::flash_fwd_kernel` 和三个 `flash_bwd_*` 内核；强制 memory-efficient 后端 + GQA 会报错，FlashAttention / cuDNN 可以。**FP32 下退回 math 后端**（没有融合内核，有单独 softmax），会显式存 T × T 矩阵。
4. **memory_calc**：BF16 的"前向后新增"（激活 + 权重副本）与公式差 1–2%；整步峰值比公式低 5–16%（公式是保守上界）。T = 4096 BF16 micro batch 1：公式 24.02 GiB（照公式在 23.6 GiB 的卡上放不下），实测 22.17 GiB，放得下。打开检查点后最大 micro batch：公式预测 3，实测 3。FP32 下公式低估约 2 GiB（T = 1024），原因是上面的 math 后端。第 15 章：每 token 每层激活 92,868 字节（公式 92,840），与 T 无关。
5. **激活检查点**：激活从 12.33 降到 1.75 GiB（14%）；每步慢 27%（723 → 919 ms），与"多约 1/3 计算"相符；MFU 55.5% → 43.6%，HFU 57.1%。
6. **MFU**：主线模型单卡 eager、T = 4096 的 MFU 55.5%（zero / PaLM 口径）；因果减半后的真实利用率 44.2%。第 15 章：32K 时一层按 zero 口径的"MFU"是 99%，真实 56%；32K 每 token 实测只贵 2.53 倍（公式不减半 4.06、因果减半 2.96，均为一层口径）。

## 四、需要主流程决定的事项

GPU 结果直接证实或推翻了下列 README / 配置里的说法。我**没有**改这些句子，也没有动 `zero/`、`configs/`：

1. **证实**（3090 + PyTorch 2.11，H100 上仍应在阶段 6 复核）：第 14 章 §4.4"GPU 上 `enable_gqa=True` 能否走 Flash 后端**尚未在 GPU 上验证**"、"从极简到生产级"表中 `04_tiled_attention.py` 一行"**尚未在 GPU 上验证**实际走的是哪个后端"、"主线进度"验证表"单卡 BF16 + SDPA"一项：BF16 下走的是 FlashAttention 内核。
2. **证实（方向）**：第 14 章 §2"eager 模式下的保守上界"——在 3090 上公式整步峰值偏高 5–16%。主线进度表"最大 micro batch 约 5"在 H100 上可能偏保守，以阶段 6 为准。
3. **证实**：`zero/model.py` 的激活检查点在 CUDA 上能用（显存与耗时符合预期；没有在 GPU 上对拍梯度）。另：`zero/tools/memory_calc.py` 的 docstring 仍写"**zero 目前没有实现激活检查点**"，已过时（`zero/model.py` 已实现）。
4. **需要补充说明**：`memory_calc` 的 FP32 公式在 CUDA 上不成立（FP32 + GQA 退回 math 后端，多存 T × T 矩阵）。主线默认 BF16，不影响主线；如果要改，可在 `memory_calc` 的"口径与局限"里加一句。
5. **推翻 / 需要改写**：第 15 章 L269"同样多的 token，用 32K 序列训练要贵 3.84 倍（……约省一半注意力运算，但比例关系不变）"和 L294 小结"约是 4K 的 3.8 倍"：一层实测只贵 2.53 倍，连因果减半的公式（2.96 倍）都高估了；3.84 倍应视为上界。原 L408（现 L439）"32K 序列下的实际 MFU 可能更低"：在 3090 上的一层里，不论哪种口径，32K 的利用率都比 4K 高（真实 48% → 56%；zero 口径 62% → 99%）。建议至少提醒"zero 日志的 MFU 在长序列下虚高，比较前先把注意力项减半"。
6. **MFU 口径**：第 14 章 §1、§6 与 `estimate_cost` 的 MFU 0.4 假设都用不减半的公式。T = 4096 时 MFU 0.4 对应的真实利用率约 0.32（5.55 / 6.96）。这不影响 $ 预算的换算（同一口径进出），但阶段 6 实测时要用同一口径比较；第 15 章 32K 阶段用 4K 的 MFU 去估算会高估费用。
7. **长上下文配置**：`configs/main/longctx.toml` 用 FSDP、没有打开 `activation_checkpointing`（继承自 pretrain.toml 的 false），注释写"32K 序列的激活很大，用 FSDP2 省显存"，第 15 章"从极简到生产级"表也写"给激活腾显存"。但 FSDP 不切激活：实测每 token 每层 92,868 字节 × 28 层 × 32,768 ≈ 79 GiB，`memory_calc configs/main/longctx.toml --strategy fsdp` 给出 101.24 GiB（超过 80 GiB），加 `--checkpointing` 才是 29.12 GiB。即使按本次测得的"公式偏保守约 8%"打折，不开激活检查点在 80 GB H100 上也放不下。建议把 `activation_checkpointing = true` 写进 `longctx.toml`（或在阶段 6 优先验证）。
8. 第 14 章开头"本章所有代码都在 CPU 上运行"：现在 code/ 里多了两个 GPU 脚本（08、09），这句话需要统一处理（我没改）。
